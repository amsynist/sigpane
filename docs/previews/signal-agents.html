Agents as first-class sessions

Today the chrome says an agent is Running in five places and nowhere says what it is doing, how long it has been at it, or how much context is left. This pass keeps every surface the size it is now and changes what each one is for: the sidebar answers which session needs me, the pane header answers what is this agent doing, and the status line answers what is it costing.

The window

Pick a situation. Session cards are clickable; the collapse button in the sidebar header shows the 58-point rail.

  • 1Context frame. The outline around a session's tile fills as its context window fills. It turns amber at 75% and red at 90%, so a session about to compact is visible from the sidebar, expanded or collapsed.
  • 2Activity line. The second line names the tool and its target while an agent works, and falls back to the directory when nothing is running. A glyph carries the state, so it never depends on colour alone.
  • 3Subagent pips. One dot per subagent: filled while it runs, hollow when it has finished. More than five collapse to a count.
  • 4Pane header absorbs the agent strip. The separate bar above the terminal goes away, so starting or ending a session no longer changes the terminal's row count. A two-point line on the header's lower edge shows running, waiting, or a real percentage when a program reports one.
  • 5Fleet footer. One segment per agent session across every tab, coloured by state, replaces the load sparkline. The approval shortcut sits directly under it.
  • 6Status line follows the focused pane. For an agent: state and turn time, model, permission mode, context, cost, lines changed. For a shell: the last command's result and the key hints it has today.
  • 7Attention pill. Appears in the titlebar only when a session you cannot see is waiting for approval. A click goes to it.

Session card states

Same 54-point card, same tile. The state changes three things only: the glyph and text on the second line, the trailing time, and the left edge for approval.

Pane header and status line

Both keep their 24 points. The header carries what is specific to the pane; the status line carries the numbers for whichever pane has focus.

Agents overview

A panel on ⌘⇧A listing every agent session in every tab and window, with its subagents underneath. Return jumps to the pane. This is the one new surface; everything else reuses space that already exists.

Where the data comes from

Nothing here needs a change to the terminal core. Everything arrives through Claude Code hooks, the status line payload, or actions the embedding API already delivers to the app.

Two things to decide with this. Tool targets are new information in the state file: today's hook stores a phase and nothing else, on purpose. The proposal stores a tool name plus a file's last path component or the first word of a command, in the same per-pane 0700 folder that is deleted when the pane closes, behind a setting. And the context numbers only exist in the status line payload, so Ghostty X would install a small wrapper that records them and then runs whatever status line command you already have.

Motion budget

The rule for this pass: nothing animates continuously on the app's main thread. A looping indicator is a Core Animation layer the render server runs by itself; everything else plays once and stops.

Decisions I need from you

  1. Tool details in the sidebar. Show tool name and file name (as drawn), or state only as today?
  2. Status line wrapper. OK for Ghostty X to wrap your Claude Code status line command to read context and cost? Without it the context frame, pie and cost are not available.
  3. Load sparkline. Retire it to an off-by-default setting, or keep it beside the fleet bar?
  4. Agents overview. Build the ⌘⇧A panel in this pass, or land the card, header and status line first?
